# AC-06 Stage A2 · Guest profile publication

## Compatibility contract before implementation

Stage A1 is `be3ac4d3297e8ad42a5950923a38e7600798f533` above `bd71090b8ab580343f0972c2e3ac15c748d21141`. The preflight matched all 1,252 committed inputs, rechecked 125 structured verdicts and 173 successful fixture process exits, and verified the four interruption/recovery pairs and four-player smoke.

A successful Garden transaction alone cannot establish whether a guest saved the projected profile. The previous wire payload has no stable revision, and monotonic merging cannot recover a class respec, loadout or appearance change after a dropped acknowledgment. Two durable additions are necessary:

- Garden `[characters] projection_origin` identifies the stream. Existing per-character records gain a `projection` descriptor containing the stream revision, the payload digest, the base profile digest and the revision at which that base was admitted. The descriptor and full profile are committed with the host Garden action.
- Profile `[character] projection_receipts` maps that Garden identifier to the highest locally committed revision and payload digest. The receipt commits in the guest's same canonical transaction as the profile. The bounded receipt list refuses a new stream when full. It does not evict older evidence.

Both additions are optional on older readable saves. Missing fields mean no projection history. Legacy Garden records still reconcile monotonic progress. A conflicting receipt or a pending projection based on a different local profile is refused for explicit review. A receipt's original digest survives subsequent local edits so reconnect can tell the difference between an exact pending replay and newer local data. The existing journal and manifest formats remain in use.

The multiplayer protocol advances from 39 to 40. Guarded and legacy peers on protocol 40 must agree on the persistence capability. An older client receives the existing version rejection, and a guarded guest must reject an acceptance lacking guarded evidence. Older installed binaries can still ignore new save keys if allowed to open the same files directly. Separate save roots or older-build exclusion remains a production cutover requirement.

## Implemented acknowledgment and ordering

- `guest_profile_projection.gd::admit/build/valid_receipts` validates the bounded descriptors and receipts. Admission reconciles maxima for older records and for a current local profile after the prior revision has been acknowledged. If the host is ahead and the guest still matches the admitted base or a verified intermediate revision, it sends the exact newest committed profile. This preserves non-monotonic fields. An unexplained local divergence or a newer guest receipt than the Garden can prove blocks admission.
- `game.gd::register_character/record_character/save_action_profile/send_committed_profile` writes the origin and profile revision with the owning Garden transaction. It publishes the committed record, including for harvest and familiarity, combat XP, class selection/learning/respec, weapon and crafting reconciliation, guarded guest appearance and expedition settlement. Departed actors retain their Garden record for reconnect. No guest profile path is in that Garden transaction.
- `game.gd::receive_character/save_guest_projection` applies the full profile and its receipt in one authorized guest profile transaction. Duplicate current revisions acknowledge the saved receipt without writing. Older revisions cannot overwrite it. A newer message must match the local committed base. An expired lease refuses before applying memory or disk changes.
- `game.gd::_report_guest_projection/guest_projection_status` reuses the reliable action RPC for `received`, `committed`, `cleanup_pending`, `aborted`, `uncertain` and `refused`. A disposition must match the active peer, Garden stream, revision and digest. Delivery status is held in session memory. The durable guest receipt is the evidence used at reconnect. Confirmed commit and cleanup-pending release persistence-dependent harvest, XP and class feedback. The cleanup warning remains in its dedicated state. An abort or refusal drops that feedback. Uncertainty blocks further writes and does not replay. Ordinary Garden and combat presentation can still reflect the host's authoritative action.
- `game_transaction.gd::_restore_guarded` handles the guest's lightweight host snapshot during a verified abort. `main_menu.gd::_launch_guarded` keeps the multiplayer node name stable by waiting for the previous queued world removal before a new launch. These were exposed by real failure and rapid reconnect tests.

## Compatibility and remaining boundaries

The existing RPC signatures are preserved. Protocol 40 carries capability and receipts in the registration catalog envelope and carries the guarded projection in the existing acceptance and profile dictionaries. Only the opt-in route issues profile acknowledgments. A protocol 39 peer cannot join a 40 host. A legacy-mode protocol 40 peer cannot join a guarded session, and a Garden with a guarded origin refuses legacy co-op. Guarded snapshots remain tied to the content manifest at admission.

Delivery acknowledgments are scoped to cooperating clients. The host cannot independently inspect a remote disk or prove that an untrusted executable ran its serializer. Loss of a connection can also drop a toast after commit. Reconnection uses committed profile data and receipts without replaying Garden rewards or historical success messages. Conflicting profile changes across different Gardens, restored backups or edits after a pending projection need review. There is no automatic conflict merge for non-monotonic fields. The bounded 64-stream receipt list requires manual handling if exhausted. Durable local exclusion for older binaries and migration of default title and persistence writers remain cutover blockers.
