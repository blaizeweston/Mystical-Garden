## Identity policy and import completion

Historical profiles with a valid 32-hex-character identity are supported, including profiles predating the content manifest. `CharacterProfile._read_profile` retains a generated random identity when the saved identity is missing or invalid. Earlier partial imports or roster entries therefore may already contain an unrelated generated identity with no verifiable source mapping. The candidate title refuses missing or invalid identities before bootstrapping or writing any destination. It does not assign an identity from the name, XP, file path, or a hash of the bytes. The original save remains available for operator review. [Legacy reader](../character_profile.gd#L106) · [Candidate import](../legacy_save_import.gd)

The explicit import validates bounded safe ConfigFile data, source profiles and receipts, Garden presence, tombstones, catalog mappings, roster identities and vacancy before mutation. It repeats selection under the native root gate. A recognized identity already used by a different or unregistered roster entry is an explicit conflict, including a byte-identical entry without an import mapping. A registered identity must still resolve to its roster entry or explicit deletion record. Slot capacity is resolved before any canonical write. Existing copies may be reconciled when exact legacy bytes and a vacant roster destination establish the relationship. Changed or ambiguous occupied destinations are preserved for review.

The candidate title commits eligible Garden and world profile copies, roster profiles, the catalog mapping, and any capacity change in one B1/B2 batch. Original legacy sources are read participants and are never rewritten. Import copies historical bytes so existing serializers can apply their ordinary migration rules on later saves. An absent destination needs no legacy backup copy. A pre-existing backup or backup scratch at a destination to be created blocks the import and is preserved. Existing backups on already present participants remain untouched.

A fully verified commit can publish ordinary import success. A cleanup-pending commit keeps the committed files and persistent warning. Uncertainty preserves evidence and blocks repeat attempts. Verified B2 recovery can restore the entire original destination set, including recorded absence, before a fresh import. Earlier partial operations may be reconciled when the old copies match, or refused when their relationship cannot be proved. No committed pre-existing Garden is removed to compensate for a subsequent roster failure. The bounded journal layout accepts the small same-root legacy import shapes using the existing primary and manifest encodings. [Journal scope](../persistence_save_layout.gd#L67) · [Title import](../main_menu.gd#L520)

## Recovery owner selection

Passive inspection and title recovery use the same seed helper for canonical paths and linked catalog or tombstone metadata. A selected slot can be blocked through the shared catalog while the review displays the separate journal anchor and its recorded members. The Developer Settings button supplies both Developer save paths and offers a selector when they have independent journal owners. Older-save recovery also searches the canonical destinations of the explicit import. Review reads and displays evidence. Confirmation reacquires the root gate, verifies the inspected selection has not drifted, and runs B2 only for the selected owner. Active leases, unresolved metadata scratch and contradictory evidence block recovery. Warnings clear only after verified resolution of the affected save set. Guest Join retains its existing admission boundary.
