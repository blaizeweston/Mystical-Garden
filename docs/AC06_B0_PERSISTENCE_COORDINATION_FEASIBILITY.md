# AC-06 B0 Persistence Operation Coordination

## Recommendation

Use one short-lived **Windows exclusive file handle** per physical user-data root. A small in-process native binding should open a permanent sentinel with `CreateFileW`, read/write access, `OPEN_ALWAYS`, sharing mode zero, and a non-inheritable handle. Treat the sharing violation as contention. A successful open is the sole proof of acquisition. Hold the handle from recovery preflight through the final canonical mutation or internal recovery, then close it. Keep the sentinel file in place. Its existence carries no ownership information. [Windows CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)

The installed engine reports **Godot 4.7.2, revision `ed1daf0bf`**. The project currently exports Windows x86-64. The probes below ran on local NTFS on Windows build 26300. ## Mechanisms evaluated

| Mechanism | Assessment |
|---|---|
| Godot `DirAccess.make_dir_absolute()` | The Windows backend uses one `CreateDirectoryW` call. One process acquired the same directory and a second was refused. The gate remained after the owner was killed, and a third process was still refused. Publishing an owner record afterward has a crash gap. Checking an owner record and then deleting the directory also permits two reclaimers to race with a new owner. Keep this option only if manual recovery is acceptable. [Godot Windows directory backend](https://github.com/godotengine/godot/blob/ed1daf0bf/drivers/windows/dir_access_windows.cpp#L211-L236) · [Windows CreateDirectoryW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createdirectoryw) |
| Godot `FileAccess.open()` and temporary files | Two independent Godot processes both opened the same sentinel in `READ_WRITE`. The runtime's standard mode does not request exclusive sharing, and ordinary write modes can truncate. Creating a unique temporary file does not acquire a shared lock name. [Godot Windows file backend](https://github.com/godotengine/godot/blob/ed1daf0bf/drivers/windows/file_access_windows.cpp#L95-L121) · [File sharing implementation](https://github.com/godotengine/godot/blob/ed1daf0bf/drivers/windows/file_access_windows.cpp#L184-L219) |
| Godot rename, copy, and remove | These are file operations without ownership semantics. For an ordinary Windows rename to an existing file, this engine deletes the destination before moving the source. The disposable missing-source probe returned an error and lost the old destination. A staged `DirAccess.rename_absolute()` therefore cannot by itself preserve the previous journal on a failed marker update. A verified replacement primitive belongs in subsequent commit hardening. [Pinned Windows rename implementation](https://github.com/godotengine/godot/blob/ed1daf0bf/drivers/windows/dir_access_windows.cpp#L288-L326) |
| Existing heartbeat leases and `SaveBatch.active` | Lease acquisition is check-then-write. The batch flag only distinguishes nested work in the same process. Also, Windows `OS.is_process_running(pid)` only consults that Godot process's child-process map. In the probe it returned false for the independently launched holder while the holder was alive. PID records and heartbeat age cannot safely authorize gate reclamation. [Slot leases](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_slots.gd:100>) · [Nested transaction handling](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/game_transaction.gd:24>) · [Pinned Windows process check](https://github.com/godotengine/godot/blob/ed1daf0bf/platform/windows/os_windows.cpp#L1516-L1538) |
| Native named Windows mutex | Viable with a native binding and abandoned-owner handling. It also needs a shared namespace, access policy, and consistent root naming across processes. The exclusive sentinel uses the shared filesystem object directly. [Windows mutex wait semantics](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject) |
| Native exclusive sentinel | Exactly one process can hold the sentinel's conflicting open at a time, even when both race to create it. The OS closes the non-inherited handle when its process terminates. A successor can acquire the existing sentinel without deleting it or proving a PID is dead. Acquisition establishes ownership of the gate. The journal still determines the save outcome. [Windows file sharing](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew) · [Windows process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process) |

## Authorization and project changes

- **Use one gate for linked participants.** Resolve canonical Garden and character paths under the same physical `user://` tree, including legacy, preview, and Developer Garden locations. The paths can be in different directories. Under the gate, resolve the participant links and owning journal before touching either file. A missing or unreadable link needs bounded legacy-journal discovery as described in the writer inventory or a blocked result if ownership cannot be established. Paths outside the supported tree require an explicit policy. [Garden and roster path binding](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/main_menu.gd:398>) · [Linked journal recovery](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_batch.gd:20>) · [Writer inventory](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/docs/AC06_PERSISTENCE_WRITE_BOUNDARY_INVENTORY.md>)
- **Give the outer operation one authorization.** `Transactions.run()` and standalone writes acquire the gate before preflight. Nested serializers and internal recovery reuse the exact authorization for the same operation and participants. Public entry points reject a foreign or reentrant request and do not reacquire through each other. Keep the protected section synchronous, with no frame or network waits, and release it on every exit. The inspected production persistence paths are synchronous. Reentrancy already occurs when an action saves the profile or Garden and through nested transaction calls. No threaded canonical-save writer was found in the inspected paths. [Outer and nested transactions](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/game_transaction.gd:24>) · [Nested profile publication](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/game.gd:1187>) · [Reward settlement](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/monster_rewards.gd:15>)
- **Apply the same boundary to direct writers and leases.** Route the inventoried imports, replacements, archives, deletes, and write-capable loads through the gate and canonical-path preflight. Browse with a non-mutating status check. Serialize lease claim, ownership checks, heartbeat updates, and release under the gate. An owner token checked before mutation prevents a session that lost its lease from resuming writes with stale memory. A free operation gate does not invalidate a still-active session lease. Stale session-lease policy stays separate from automatic kernel-handle release. [Lease operations](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_slots.gd:100>) · [Roster browsing](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/character_slots.gd:38>) · [Direct Garden deletion](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_slots.gd:202>)
- **On restart, acquire first and inspect recovery second.** A terminated holder leaves the sentinel file and any transaction artifacts intact. The next owner resolves recovery before permitting affected writes. A blocked recovery preserves its evidence and releases the short-lived gate so other known-unrelated saves can proceed. Keep affected participants blocked across restarts using the existing journals and links. If participants cannot be bounded safely, block the potentially affected set.
- **Concurrency tradeoff.** Unrelated slots can be open at the same time and can save in turn. B0 serializes their short file operations within one data tree. Truly simultaneous writes to unrelated slots are possible with per-participant native handles, a deterministic acquisition order, and revalidation of the complete linked set under lock. That adds complexity and is unnecessary for B0. Two Garden slots that share a roster profile must never acquire independent authorization to write that profile.

## Minimal implementation plan and limits

1. Prove the native binding in editor and packaged Windows runs. The usual GDExtension path adds a DLL to the distributed build. The current installer copies only the milestone EXE, so it would need to install and verify the native library too. Keeping a single EXE would instead require a native module built into matching editor and export templates. A C/C++ compiler was not found on the current PATH or through the standard Visual Studio query. Native build and packaging feasibility remains to be verified. [Godot GDExtension library packaging](https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/gdextension_file.html) · [Current EXE installation](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/tools/release_latest.ps1:95>)
2. Add the shared acquire/release boundary and operation authorization to the existing persistence layer. Connect the two serializers, outer transactions, recovery, and direct slot writers. Keep existing save and journal formats. Treat an unavailable lock backend, contention, and pending recovery as explicit blocked states rather than proceeding without protection.
3. Verify the source and packaged paths on disposable files before enabling protected writes. Keep serializer-error propagation, harvest feedback, and commit-marker hardening in their existing AC-06 stages.

The evidence covers cooperating Windows processes on local NTFS that use the same sentinel. Other operating systems, network or redirected storage, external save edits, older game binaries that bypass the gate, and sudden power loss are outside the verified guarantee. The gate serializes access. It does not make a two-file replacement crash-atomic.

## Disposable evidence and acceptance tests

| Run | Observed result |
|---|---|
| `ac06-b0-win-ntfs-primitives` | Godot directory acquisition admitted one owner and left the gate after a kill. Ordinary Godot file open admitted both owners. Direct Win32 `CreateFileW` rejected the contender with sharing violation 32, admitted exactly one process in a race for an absent sentinel, and allowed reacquisition after a kill with the file still present. [Primitive evidence](B0_PRIMITIVE_EVIDENCE.json) |
| `ac06-b0-linked-recovery-harness` | Two contenders representing a Garden and a roster profile in different directories both failed to acquire the shared native handle. The harness verified unchanged pair and journal bytes until the killed owner was replaced. The successor ran existing recovery via the profile link and restored both originals. The separate failed-rename case removed the old destination. This was a harness around existing recovery, so production writer integration remains unverified. [Linked and rename evidence](B0_LINKED_EVIDENCE.json) |

Implementation acceptance should cover these additional paths in the actual game and package:

1. Race two game processes for one fresh sentinel. Verify exactly one acquires, and the loser cannot create staging, backup, archive, or tombstone artifacts. Repeat after clean release and forced termination.
2. Hold authorization across a Garden and a roster profile in separate directories. Attempt writes, direct import, deletion, and recovery from another game process through each participant. Repeat with two Gardens sharing a roster profile and with relative and absolute aliases for the same path.
3. Kill the holder before and after the first replacement. Check that a restarted game acquires the gate, preserves unreadable or unresolved journals, recovers a readable legacy journal through either participant, and blocks writes until the pair is verified. Test a blocked recovery, then remove the fault and retry.
4. Exercise nested serializers and internal recovery under one authorization. Check that unrelated reentrant operations fail promptly, every failure path releases the handle, and a stale former session owner cannot resume writing after lease handoff.
5. Verify an unrelated slot can save when the gate is free even while another known save set is pending. Verify that a missing native library fails closed in the packaged build.

All probes used disposable files. The project and player saves were kept read-only.
