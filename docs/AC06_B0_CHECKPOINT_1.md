# AC-06 B0 Checkpoint 1 — Shared persistence authorization

Checkpoint 1 adds an opt-in authorization API and a Windows x64 GDExtension. The only caller is the new regression fixture. B0 remains open until every canonical writer is covered. No production serializer, SaveBatch operation, slot lease, gameplay path, or save format was edited. Validation ran against an isolated project copy, disposable exports, and separate APPDATA roots.

## Implementation

- `PersistenceAuthorization.run(paths, callback)` (preload `persistence_authorization.gd`) opens a single short operation against the fixed `user://.mystical-garden-persistence.lock` sentinel. Windows grants exclusive access with `CreateFileW`, `OPEN_ALWAYS`, zero sharing, and a non-inheritable handle. The sentinel can remain after release or termination. [Authorization boundary](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_authorization.gd>) · [Native source](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/tools/native/persistence_lock/native_lock.c>) · [CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
- The API accepts ordinary `user://` file paths under the engine's user-data root. It rejects traversal, UNC, device, alternate-stream and short-name forms, trailing dots or spaces, reparse points and case-sensitive ancestry detected by Godot. The DLL requires a fixed local NTFS volume, rejects hard-linked or reparse-point sentinels and existing participants, and reports native acquisition failures. The backend is discovered through ClassDB so a missing class or incompatible interface yields `ERR_UNAVAILABLE` before the callback. [Authorization boundary](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_authorization.gd>) · [Windows directory checks in Godot](https://github.com/godotengine/godot/blob/ed1daf0bf/drivers/windows/dir_access_windows.cpp)
- `run_nested(token, paths, callback)` accepts the current token and an exact subset of the declared paths. A new outer call while one is active returns `ERR_BUSY`. Foreign and expired tokens or an expanded path set return `ERR_UNAUTHORIZED`. The outer call releases the handle after a synchronous callback, including when the callback returns an error, and keeps its returned value separate from the boundary status. Native instance destruction also attempts to close any held handle. Callbacks must finish synchronously. [Authorization fixture](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/tests/persistence_authorization.gd>)
- The DLL keeps the four native methods from the prototype. Integrated `acquire(path, participants)` adds the declared paths for native alias checks. `release()`, `is_held()`, and `last_error()` are unchanged. There is no save serialization or journal logic in the extension. [Extension descriptor](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/assets/native/persistence_lock/persistence_lock.gdextension>) · [Native source](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/tools/native/persistence_lock/native_lock.c>)

## Build and package

Tested with Godot **4.7.2.stable.official.ed1daf0bf**, the matching stock Windows x86-64 release template, and portable **LLVM-MinGW 20251104**, Clang **21.1.5** (`8e2cd28cd4ba46613a46467b0c91b1cabead26cd`), UCRT, target `x86_64-w64-windows-gnu`. ## Remaining risks

The lock serializes cooperating operations across one user-data root, including unrelated slots. Existing writers do not use it yet, so it does not prevent concurrent live writes at this checkpoint. Session leases still own sessions. Later writer integration must declare all canonical participants, run recovery and the mutation within the same authorization, and cover legacy imports, deletion, and archive paths.

Validation covered local Windows x64 NTFS. Other OSes, architectures, filesystem types, redirected roots, and long paths are outside this checkpoint. The boundary assumes other software will not replace a parent directory or change its reparse attributes during an operation. It is a coordination boundary for cooperating game processes, with no protection against external filesystem tampering. No player EXE was replaced and no live player save was used.
