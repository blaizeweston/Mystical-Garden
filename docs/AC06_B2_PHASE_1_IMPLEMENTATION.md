# AC-06 B2A Phase 1 — Durable transaction evidence and safe publication

B2 Phase 1 is implemented on the opt-in SaveBatch route. Production activation remains disabled. Legacy SaveBatch and its callers retain their current behavior. Restart discovery verifies evidence and blocks writes. Executing restart restoration and cleanup remains a later phase.

## On-disk protocol

All four new leaves are exact suffixes of the canonical journal anchor. A Garden-anchored operation uses `garden.cfg.txn_expected` for prepared evidence, `garden.cfg.txn_receipt` for verified-commit cleanup, `garden.cfg.txn_previous` for the uncommitted fallback, and `garden.cfg.txn_publish` for publication scratch. Only the anchor owns these artifacts. Existing `.transaction`, `.txn_link`, `.txn_stage` and `.recovery` paths retain their existing naming and roles.

- The version 1 manifest is bounded to 8 KiB and canonical JSON. It stores a 128-bit attempt ID, canonical anchor, strictly sorted unique participants, each participant's expected existence, length and SHA-256, and hashes of both journal images. Strict re-encoding rejects duplicate fields and noncanonical representations. The primary ConfigFile schema is unchanged. A fixed trailing whitespace sequence binds newly produced journal bytes to their attempt without adding a field. Both images are checked by the existing bounded journal parser before writing. Legacy journals need no trailer to remain readable. [Evidence definition](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_evidence.gd>)
- Before writing any transaction artifacts, SaveBatch rechecks the locked observations, captures original bytes or absence, and budgets the complete operation against the planner's file, directory, 32 MiB record-scan and 64 MiB observation limits. The conservative budget reserves primary, fallback and journal scratch, a manifest or receipt, old and new participant bytes, a restore scratch, links and leases. It includes existing journal-scan usage and future directory entries. It rejects oversize or unreadable journal images before publishing. The native sentinel is acquired separately and may exist before this check. [Footprint](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_recovery_plan.gd>) · [Finalization](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_batch.gd:185>)
- The writer publishes and verifies an uncommitted primary, the prepared manifest and the byte-identical fallback before replacing canonical files. It checks each stage and publishes each link from an owned sibling scratch. The native same-directory `MoveFileExW` implementation uses replacement and write-through without cross-volume copy. GDScript requires the live token and exact scope, and the native instance independently requires the held handle, acquired paths and ordinary local NTFS leaves. Guarded replacement, including live restoration, uses this primitive. There is no destructive Godot rename fallback. The backend's replacement capability is checked before invoking the staged action. [Authorization](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_authorization.gd>) · [Native operation](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/tools/native/persistence_lock/native_lock.c>)
- A matching committed marker and matching participant bytes confirm commit. The prepared manifest is then moved to the receipt. Cleanup deletes the primary before the receipt. A receipt publication or cleanup failure keeps the confirmed-commit disposition. If marker publication fails, live B1 restoration requires the readable exact uncommitted primary and compatible participant bytes. Losing the primary leaves the fallback and prepared evidence blocked as `UNCERTAIN`, even if they are readable. The fallback does not decide whether a marker had been published. [SaveBatch outcomes](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_batch.gd:330>)
- The planner discovers the new artifacts by anchor and by reverse participant membership, including a receipt after primary deletion. It rejects conflicting membership, marker or attempt binding, bad fallback, malformed artifacts, and mismatched committed bytes or length. Pending B2 artifacts remain blocked by the ordinary writer and do not authorize restart recovery execution. Unbound or unreadable records can conservatively block broader discovery. [Planner](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_recovery_plan.gd>)

### Participant scope

The legacy gameplay wrapper normally saves `game.progress` and the participating local profile. Its guest branch skips the local-profile serializer, and nested calls join the active batch. The shared `SaveBatch.write` also serves app and network settings, roster catalogs and deletion tombstones. Static inspection does not establish that no such call can stage during an active gameplay batch. A pair-only production rule is therefore deferred until writer migration isolates unrelated settings and metadata and proves the expected scope at runtime. Phase 1 preserves the existing up-to-16 canonical participant contract subject to footprint limits. A three-participant disposable commit passed.
