# AC-06 B0 Checkpoint 2A-1 — Read-only participant discovery

Implemented an opt-in reader beside SaveBatch. Its only caller is the regression fixture. SaveBatch, Checkpoint 1 authorization, production writers, gameplay, save and journal formats, and the release tools were left unchanged. No live save was opened and no player EXE was replaced.

## Implementation and changed files

- `persistence_recovery_plan.gd` and its UID add `discover(paths)` and `revalidate(previous, paths, token)`. Discovery uses the supplied canonical files, scans the bounded legacy, Garden slot, roster, Preview, and Developer Garden namespaces, and follows both participant links and reverse journal entries. It includes journal anchors, even when absent from the entry map, and preserves recorded original bytes and absence. It validates the complete selected plan, rejects overlapping journals, and reports a state and refusal reason. - Discovery returns `healthy`, `empty`, `busy`, `pending_recovery`, `ambiguous` or `invalid`. Healthy means canonical files exist and there is no relevant recovery evidence. It does not validate gameplay save contents. Busy indicates a fresh foreign session marker. A valid journal returns pending with candidate authorization paths. A blocked plan has no authorization paths. Only an unchanged, valid pending plan revalidated under the live token is marked `recovery_ready`. That flag is scoped to the callback, and this checkpoint provides no recovery executor. [Discovery and locked comparison](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/persistence_recovery_plan.gd>)
- Revalidation uses the existing `run_nested` token and exact declared path subset. The caller supplies `authorization_paths` to Checkpoint 1, covering canonical participants and their recovery artifacts so the native backend can check existing file identities. A changed destination, participant set, observation, or authorization path set requires a fresh preview. ## Limits and interface implications

- Existing SaveBatch records and raw links keep their format. The reader accepts the ConfigFile structure emitted by SaveBatch, including numeric and encoded PackedByteArray values. A syntax screen precedes Godot parsing so arbitrary Variant constructors cannot be used to load objects or resources. Hand-edited records outside the emitted structure, unsupported paths and exceeded bounds fail closed. An unidentifiable journal can block a wider namespace because it may reference a participant whose link is missing. [SaveBatch writer](<C:/Users/sutte/Desktop/The Garden Game development/Mystical Garden/save_batch.gd:41>) · [Godot ConfigFile parser](https://github.com/godotengine/godot/blob/ed1daf0bf/core/io/config_file.cpp)
- Bounds are 4,096 entries per inspected directory, 16 entries per journal, 8 MiB per observed file, 32 MiB of aggregate journal data, and 64 MiB of aggregate participant observations. Slot namespaces follow the current three world slots and 128 roster slots per supported tree. Custom roots and aliases outside those layouts are outside this checkpoint.
- No Checkpoint 1 API change is required for plans whose directories already exist. A missing parent can be discovered read-only, but acquisition still rejects it until the separately scoped directory bootstrap exists. Optimistic discovery is not an ownership claim. Existing hard-link validation is provided by native acquisition for declared paths. Session marker reads are advisory for planning. Production integration still needs explicit lease ownership checks under authorization.
- The existing root lock serializes participating operations. It cannot exclude older executables or external programs that bypass it. This fixture uses a controlled change between preview and acquisition. It does not exercise production writer contention, recovery execution, commit durability, or a full installer run.
